# Gemma 4 absolute performance forecast on 8x Ascend 950DT

This is a reproducible engineering forecast for capacity planning and benchmark
acceptance. It is **not** a measured 950DT result. Every absolute value below is
generated by `theory.py`; hardware utilization and latency assumptions are
kept explicit so profiler data can replace them later.

## Hardware and serving contract

Huawei publishes 144 GB HBM, 4 TB/s HBM bandwidth and 2 TB/s interconnect
bandwidth for one Ascend 950DT. The Ascend 950 series is specified at 1 PFLOPS
for FP8/MXFP8/HiF8 and 2 PFLOPS for MXFP4. The same announcement positions
950DT for decode and training. See the
[Huawei Connect 2025 keynote](https://www.huawei.com/en/news/2025/9/hc-xu-keynote-speech).

| Resource | One 950DT | Eight 950DT used by this model |
| --- | ---: | ---: |
| HBM capacity | 144 GB | 1.152 TB raw |
| HBM bandwidth | 4 TB/s | 32 TB/s raw aggregate |
| MXFP8 peak | 1 PFLOPS | 8 PFLOPS raw aggregate |
| MXFP4 peak | 2 PFLOPS | 16 PFLOPS raw aggregate |
| Interconnect | 2 TB/s | Modelled through TP/EP efficiency, not multiplied as a bus |
| BF16 peak | 0.5 PFLOPS assumed | 4 PFLOPS assumed |

The BF16 number is not an official 950DT specification. It is an explicit
planning inference of one half the published MXFP8 peak and must be replaced by
the measured BF16 roofline when hardware is available.

- Dense 31B topology: one eight-card node, TP=8.
- 26B-A4B topology: one eight-card node, TP/EP=8.
- B0 original: BF16 eager autoregressive target and generic operator flow.
- B3 optimized: mixed MXFP target/draft, DSpark, FULL graph, device-resident
  adaptive lengths, fused FIA prolog/KV write, plus MegaMoe for A4B.
- Prefix cache is off. There is no external queue. Every row is a synchronized
  closed batch of equal-length requests, admitted without scheduler throttling.
- TTFT is the batch prefill time; TPOT is the per-request inter-token interval;
  `tok/s` is aggregate output throughput; `req/s` includes prompt plus all
  output tokens.

## Workloads

| Workload | Input/output | Representative production use |
| --- | ---: | --- |
| Decode-heavy | 128/512 | Code generation, long chat answer |
| Balanced | 2048/256 | Online assistant, tool use |
| Long 8k | 8192/128 | RAG, document question answering |
| Long 32k | 32768/128 | Long-document analysis |

The sweep uses concurrency 1/4/8/16/32/64. This exposes the expected crossover:
low concurrency benefits most from quantization, speculative decoding and
graph/launch removal; high concurrency amortizes the original weight read and
becomes increasingly limited by compute, KV traffic and communication.

## Model equations and assumptions

For each batch, the B0 output-token roofline is the minimum of HBM and BF16
compute limits:

```text
B0 decode tok/s = min(
  C * aggregate_HBM_BW * HBM_eff(C) * topology_eff(C) / BF16_weight_union(C),
  aggregate_BF16_FLOPS * cube_eff(C) * topology_eff(C) / (2 * active_params)
)
```

The B3 value is the minimum of the calibrated relative curve, mixed-precision
HBM and compute roofs, and a graph-replay step-latency floor:

```text
B3 decode tok/s = min(
  B0 * calibrated_B3/B0_decode,
  mixed_HBM_roof * ideal_speculative_ceiling,
  mixed_compute_roof * ideal_speculative_ceiling,
  C / minimum_batch_step_latency
)
```

Prompt FLOPs include active-weight linear work and the real Gemma 4 pattern of
five 1024-token sliding layers followed by one global layer. Batch TTFT is
prompt FLOPs divided by effective BF16 throughput plus a 6 ms fixed term. B3
TTFT applies only the calibrated prefill-side gains; speculative decoding is
not credited to prompt processing.

| C | 1 | 4 | 8 | 16 | 32 | 64 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Dense HBM efficiency | 62% | 68% | 72% | 75% | 77% | 78% |
| Dense TP efficiency | 82% | 84% | 85% | 85% | 84% | 82% |
| Dense prefill Cube efficiency | 42% | 48% | 52% | 55% | 57% | 58% |
| A4B HBM efficiency | 50% | 58% | 62% | 66% | 70% | 72% |
| A4B EP efficiency | 75% | 72% | 68% | 64% | 60% | 58% |
| A4B prefill Cube efficiency | 32% | 38% | 42% | 45% | 47% | 48% |

The A4B batch weight union is `min(26B total, 4B active * concurrency)`;
different requests may route to different experts. The B3 single-stream target
step floors are 0.55 ms for 31B and 0.35 ms for A4B, increasing 6% per doubled
concurrency. These are calibration assumptions, not hardware specifications.
Use a central-value planning band of -25%/+20% for throughput and the inverse
band for latency until measurements replace the efficiency and floor terms.

## How to use the forecast

Generate either complete table directly:

```bash
python benchmarks/gemma4_a5/theory.py 31b --absolute --format markdown
python benchmarks/gemma4_a5/theory.py 26b-a4b --draft-cost-ratio 0.10 \
  --absolute --format markdown
```

Treat the first 950DT profile as model calibration rather than a pass/fail
surprise. Replace, in order: the BF16 peak inference; per-concurrency HBM,
Cube and TP/EP efficiencies; single-step floor; DSpark acceptance and draft
cost; then the fixed prefill intercept. A measured row is accepted only when
the checkpoint, topology, graph mode, scheduler limits, prefix-cache state,
input/output lengths and concurrency match this contract.

Prefix caching is deliberately excluded from the original/optimized delta
because both paths can reuse the same prefix. For a measured hit rate `h`, the
first-order cached prefill estimate is `fixed + (uncached - fixed) * (1-h)`;
validate it separately because block alignment, suffix length and scheduler
overlap determine the realized TTFT.
