# 04 量化适配

[上一篇：特性接入](03_特性接入情况.md) | [返回总览](README.md) | [下一篇：精度、性能与调优](05_精度性能基线与调优.md)

## 1. 本篇做了什么

这一篇说明 Gemma4 的 ModelSlim W8A8 适配。主要处理四个问题：

| 工作 | 具体处理 | 目的 |
|---|---|---|
| Global K=V 权重加载 | K 权重同时映射到 Packed QKV 的 K/V Slot | 支持合法缺少独立 `v_proj` 的 Checkpoint |
| MoE Expert 路径映射 | 对齐 Runtime Module 与 Quant Description Prefix | 正确找到 26B MoE 专家权重 |
| Expert Activation | 根据模型配置选择 GELU-TANH 或 SwiGLU | 保持量化与 BF16 的数学语义一致 |
| A5 C8 KV Cache | 接入 `store_kv_block`，保持 KV Sharing 写入规则 | 减少格式转换，同时避免 Target 覆盖 Producer Cache |

量化适配不是简单地把 Linear 从 BF16 换成 INT8。它会改变权重存储、Shard 描述、Activation、Fused Kernel、KV Cache Format 和 Graph Shape，因此需要重新核对完整的数据流。

## 2. 为什么需要单独适配

通用 W8A8 实现通常隐含以下模型结构：

```text
Q、K、V 都有独立权重
MLP/Expert 使用固定 SwiGLU
量化描述与 Runtime Module 使用相同名称
KV Cache 由当前 Layer 正常写入
```

Gemma4 并不完全满足这些假设：

- 31B 和 26B 的 Global layer 使用 K=V；
- 26B MoE 的 Runtime Expert 路径与量化描述前缀可能不同；
- Gemma4 Expert 使用 GELU-TANH，而不是默认 SwiGLU；
- E2B/E4B 的 KV-Sharing Target 只能读 Producer Cache；
- A5 C8 Cache 需要对应 Custom Op 和构建依赖。

如果不处理这些差异，可能出现两种失败：

1. **显式失败**：启动时找不到权重、模块或 Custom Op。
2. **静默失败**：服务能启动、Shape 也合法，但 Activation 或权重映射错误，最终持续掉点。

第二类问题更危险，因为日志看起来正常，只能通过单层对照或全量精度发现。

## 3. 我们如何分析量化问题

量化适配按下面的顺序进行：

```text
核对 Checkpoint Tensor
  -> 核对 Quant Description
  -> 核对 Runtime Module Path
  -> 核对 Packed/Shard Mapping
  -> 核对 Activation 与 Fused Kernel
  -> 核对 KV Cache Format
  -> 组合 Eager/Graph、TP/EP 和多模态验证
```

每一步都保留 BF16 控制组：

| 对照结果 | 优先检查 |
|---|---|
| BF16 正常，W8A8 加载失败 | Quant Description、Prefix、Packed Mapping |
| BF16/W8A8 都能启动，W8A8 持续掉点 | Activation、Scale、Shard、Quant Cache |
| Eager 正常，Graph W8A8 失败 | Capture Shape、C8 Cache、Graph Param |
| Dense 正常，MoE W8A8 失败 | Expert Prefix、Activation、Router/Combine |

一次实验尽量只改变一个变量，避免同时更换 Checkpoint、Graph Mode 和并行配置后无法判断原因。

## 4. 问题一：Global Layer 缺少 `v_proj`

### 4.1 现象

加载 31B 或 26B 的量化权重时，可能出现：

```text
KeyError: ...v_proj.weight
```

通用 QKV Loader 期待 Q、K、V 三份权重，但 Gemma4 Global layer 的 Checkpoint 可能只提供 Q 和 K。

### 4.2 原因分析

对 `attention_k_eq_v=true` 的 Global layer，K Projection 同时承担 Key 和 Value：

```text
Checkpoint K
  -> Packed QKV K Slot
  -> Packed QKV V Slot
```

因此，没有独立 `v_proj` 是合法模型语义，不代表 Checkpoint 损坏。

但不能把 Loader 改成“缺 V 就跳过”，因为以下情况仍然必须报错：

- 非 K=V layer 缺少 V；
- Q 或 K Shard 缺失；
- Packed Mapping 不完整；
- Quant Description 与 Tensor 列表矛盾。

### 4.3 解决方案

Loader 根据当前 Layer 的模型配置做窄范围处理：

1. 检查 `attention_k_eq_v`；
2. 确认 Q/K Quant Description 完整；
3. 将 K Shard 同时加载到 Packed QKV 的 K/V Slot；
4. 非 K=V layer 继续严格要求独立 V；
5. 其他缺失权重保持原错误检查。

### 4.4 收益

- 支持 Gemma4 合法的 K=V Checkpoint；
- 不需要伪造一份 V 权重；
- 不会掩盖其他模型真正损坏的 Checkpoint；
- BF16 与 W8A8 使用同一 K=V 语义。

## 5. 问题二：MoE Expert 路径不一致

### 5.1 现象

26B MoE 的 Runtime Module 与 ModelSlim Quant Description 可能使用不同路径：

```text
Runtime Module : .moe.experts
Quant Desc     : .experts
```

如果直接按字符串精确匹配，Loader 找不到专家量化配置；如果做全局字符串替换，又可能影响其他模型。

### 5.2 原因分析

权重加载需要同时理解：

- vLLM 中 Module 的真实层级；
- ModelSlim 导出的 Quant Prefix；
- Packed Expert 的 Shard 规则；
- Shared Expert、Router 与普通 Expert 的区别。

`.experts` 并不是所有模型都等价于 `.moe.experts`。宽泛替换可能误改：

- 其他模型的 Nested MoE；
- Shared Expert；
- Router；
- Dense MLP；
- 已经包含 `.moe.experts` 的路径。

### 5.3 解决方案

路径映射只对明确的 Gemma4/Gemma4Text Expert Module 生效：

```text
识别 Gemma4 Model Type
  -> 识别 Expert Path
  -> 对齐 Quant Prefix
  -> 保留非 Gemma4 原路径
```

对应单测需要证明：

- Gemma4 和 Gemma4Text 均能映射；
- Dense Module 不改；
- 非 Gemma4 不改；
- Packed Module 完整；
- Mixed Shard 缺失继续报错。

### 5.4 收益

- 26B MoE Expert 权重能够正确加载；
- 修改不会扩散到其他 MoE 模型；
- 映射规则可以由模型类型和模块语义解释；
- 后续 ModelSlim 格式变化更容易定位。

## 6. 问题三：GELU-TANH 与 SwiGLU

### 6.1 现象

量化 MoE 服务可能正常启动，但精度异常，没有明显 Shape 或 Kernel 报错。

### 6.2 原因分析

部分 Fused MoE 路径默认使用 SwiGLU：

$$
\mathrm{SwiGLU}(a,b)=\mathrm{SiLU}(a)\odot b
$$

Gemma4 使用 GELU-TANH：

$$
\mathrm{GELU}_{tanh}(x)
$$

两者不是同一函数。某些 Kernel 接口下，Tensor Shape 仍然兼容，因此错误不会以 Crash 形式出现，而是每个 Expert 都执行了错误的非线性变换。

### 6.3 解决方案

- 从模型配置读取 Activation；
- GELU/GELU-TANH 进入对应 Expert Path；
- 只有明确使用 SwiGLU 的模型进入 Fused SwiGLU；
- 浮点与量化路径共享相同 Activation 语义；
- 为不同 Activation 增加单层输出对照。

### 6.4 收益

- W8A8 不再因为默认激活函数改变模型数学语义；
- Dense/MoE、浮点/量化的行为保持一致；
- 后续新增模型可以复用按配置选择 Activation 的能力；
- 避免“能启动但持续掉点”的静默错误。

## 7. 问题四：A5 C8 KV Cache

### 7.1 做了什么

A5 C8 Reshape/Cache 路径使用更适合设备计算与访存的 KV 格式，并依赖 `store_kv_block` Custom Op。

构建和运行路径需要保证：

- Custom Op 被正确编译和注册；
- C8 Cache Shape 与 Quant Description 一致；
- Graph Capture 能处理对应 Buffer；
- KV-Sharing Target 不执行 Cache Write；
- NZ/C8/普通 Cache Path 使用相同 Owner 语义。

### 7.2 遇到的问题

缺少 Custom Op 时可能出现启动符号错误或进入非预期 Fallback。更隐蔽的问题是：普通 BF16 Path 已跳过 KV-Sharing Target 写入，而 C8 Path 仍然写 Cache，导致 Producer 数据被覆盖。

### 7.3 解决方案与收益

我们把 Cache Write 条件统一到模型语义：

```text
当前 Layer 是 KV Producer
  -> 写入 Cache

当前 Layer 是 KV-Sharing Target
  -> 保留 Cache 引用并读取
  -> 不写入 Producer Cache
```

C8 优化可以减少后续 Decode 的格式转换和访存成本，但不改变 Cache 所有权。这样量化优化与 E2B/E4B KV Sharing 可以正确组合。

## 8. 验证方案

### 8.1 分层验证

1. ModelSlim 配置解析单测；
2. Quant Prefix 和 Packed Mapping 单测；
3. 权重加载完整性；
4. Global/Sliding 单层输出；
5. Dense/MoE 服务拉起；
6. 文本与图片 Smoke；
7. Eager/Graph 对照；
8. 小规模精度；
9. 全量精度；
10. 固定 Workload 性能；
11. TP/EP 和 KV Sharing 组合。

10 题或少量 Prompt 只用于快速发现明显错误，不能作为正式精度基线。

### 8.2 当前性能证据

现有基线覆盖：

- 31B Dense W8A8；
- 26B MoE Only-Experts W8A8_DYNAMIC；
- v1 Engine；
- TP1；
- PIECEWISE；
- 文本和图片 Workload；
- 100% 请求成功。

详细数据见 [05 精度、性能基线与调优](05_精度性能基线与调优.md)。

为什么文本和图片要分别测试？多模态请求的 Prefill 更长，Encoder/Projector 与语言模型的耗时占比也不同。W8A8 对 Decode MLP 的收益可能被视觉 Encoder 或长 Prefill 稀释，拆开 Workload 才能看清优化发生在哪一段。

## 9. 当前结果与边界

### 已完成

- 31B/26B Global K=V 量化权重映射；
- 26B MoE Expert Prefix 映射；
- GELU-TANH 量化 Expert 路径；
- A5 C8 Cache 所需构建与写入语义；
- 31B Dense 和 26B MoE W8A8 性能基线。

### 尚不能直接外推

当前结果不能自动代表以下场景已经验证：

- E2B/E4B 所有量化 Checkpoint；
- 所有 ModelSlim 导出版本；
- A2/A5 的全部组合；
- TP2/TP4 与 EP；
- 量化 MTP；
- 超长上下文；
- FULL_DECODE_ONLY。

新增 Checkpoint 时仍需重新核对 Quant Description、Tensor 列表、模型 Revision、并行配置和 Graph Mode。
