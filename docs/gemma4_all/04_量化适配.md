# 04 量化适配

[上一篇：特性接入](03_特性接入情况.md) | [返回总览](README.md) | [下一篇：精度、性能与调优](05_精度性能基线与调优.md)

## 1. 为什么量化适配不只是替换 Linear

W8A8 会改变：

- 权重存储和 shard 描述；
- activation dtype/scale；
- fused MLP kernel；
- KV cache format；
- graph capture shape；
- ModelSlim 的模块名称匹配。

Gemma4 又有 K=V、MoE experts、GELU-TANH 和 E2/E4 KV sharing，因此通用 W8A8 loader 不能只按 `q_proj/k_proj/v_proj` 和 SwiGLU 假设工作。

量化最容易制造一种“看起来成功”的失败：权重能加载，服务能启动，输出也是流畅中文，但模型实际上已经不是原来的数学函数。原因是量化不只压缩数值精度，还经常替换 loader、packed module 和 fused kernel。只要激活函数或权重映射选错，shape 仍可能完全合法，系统不会 crash，精度却会持续偏低。

### 1.1 我们怎样规划量化适配

我们没有直接拿完整 W8A8 服务做黑盒测试，而是按语义逐层确认：

```text
先对齐 checkpoint tensor 与 runtime module
  -> 再验证 K=V 的 packed QKV mapping
  -> 再验证 Dense/MoE activation
  -> 再验证 KV cache format
  -> 最后组合 graph、TP/EP 和多模态
```

每一步都保留 BF16 控制组。BF16 正常而 W8A8 加载失败，优先看 quant description 和 prefix mapping；两者都能启动但 W8A8 掉点，则优先看 activation、scale、packed shard 和量化 cache，而不是立即怀疑 attention 主干。

## 2. 31B global layer 的 K=V

### 2.1 报错

量化加载可能出现：

```text
KeyError: ...v_proj.weight
```

这个报错表面上很合理：通用 QKV loader 期待 Q、K、V 三份投影，checkpoint 却只有 Q 和 K。若不了解 global layer 的 K=V 设计，最自然的修复是补一份 V 或直接跳过缺失项；前者可能加载错误权重，后者可能留下未初始化 slot。

### 2.2 合法缺失与错误缺失

对 `attention_k_eq_v=true` 的 global layer：

- checkpoint 没有独立 V 可以是合法；
- K 权重应映射到 QKV 的 K/V slot；
- q/k 描述存在时，缺 V 不应报错。

但以下情况仍必须报错：

- 非 K=V layer 缺 V；
- Q 或 K shard 缺失；
- packed module mapping 不完整；
- quant description 与 tensor 列表矛盾。

### 2.3 设计原则

量化 loader 的容错必须是“模型语义驱动的窄容错”，不能写成“找不到 V 就跳过”。

最终处理流程是：

```text
读取当前 layer 的 attention_k_eq_v
  -> 确认 q/k quant description 存在
  -> 将 K shard 同时装入 packed QKV 的 K/V slot
  -> 保留非 K=V layer 对缺失 V 的严格报错
```

这样既支持合法共享，也不会把真正不完整的 checkpoint 洗白。

## 3. 26B MoE expert 路径映射

模型模块和量化描述可能使用不同前缀：

```text
runtime module : .moe.experts
quant desc     : .experts
```

ModelSlim mapper 只对 Gemma4 专家路径做明确映射。宽泛字符串替换可能误伤：

- 其他模型的 nested MoE；
- shared expert；
- router；
- dense MLP。

路径映射之所以危险，是因为它发生在权重加载阶段。一个过宽的 `.replace(".experts", ".moe.experts")` 可能让目标 Gemma4 起得来，却悄悄改写其他模型的 shared expert 或嵌套模块。上库方案必须同时证明“Gemma4 被正确映射”和“非 Gemma4 保持原样”，后者通常比前者更容易在评审中被忽略。

需要单测：

- Gemma4/Gemma4Text 都映射；
- 非 Gemma4 不改；
- packed modules 完整；
- mixed shard 继续报错。

## 4. GELU-TANH 与 SwiGLU

### 4.1 错误为何不一定 crash

若量化 MoE 硬编码 SwiGLU，tensor shape 仍可能兼容，服务也能启动，但：

$$
\mathrm{SwiGLU}(a,b)=\mathrm{SiLU}(a)\odot b
$$

与：

$$
\mathrm{GELU}_{tanh}(x)
$$

不是同一函数。模型数值语义已经改变。

这是量化适配中最值得警惕的案例。Fused MoE kernel 往往根据输入 shape 选择计算路径，SwiGLU 与 GELU-TANH 的 tensor 形状在某些实现里都能满足接口，所以启动日志看不出异常。只有对照单层输出或全量精度，才会发现每个 expert 都在执行错误的非线性函数。

### 4.2 修复

- 从模型配置读取 activation；
- GELU/GELU-TANH 使用对应 activation path；
- 仅 SwiGLU 模型进入 fused SwiGLU；
- 量化和非量化保持相同 activation 语义。

收益不是单纯“避免报错”，而是让 BF16 与 W8A8 共享同一模型语义定义。量化路径只改变数值表示和 kernel 实现，不再自己发明模型结构。

## 5. A5 C8 cache

A5 的 C8 reshape/cache 优化依赖 `store_kv_block` custom op。构建系统需要包含该 op，否则：

- 启动时缺符号；
- C8 path 不可用；
- graph capture 可能进入非预期 fallback。

KV-sharing target 在 C8/NZ path 中也必须跳过 cache write，不能只修普通 BF16 path。

C8 cache 的目标是让 KV 以更适合设备计算和访存的格式保存，减少后续 decode 的转换开销。但格式优化不能改变“谁有权写 cache”。如果普通 BF16 path 已正确跳过 KV-sharing target，而 C8 path 又重新写入，功能测试可能只在量化图模式下失败，看起来像量化精度问题，实际仍是 cache owner 被破坏。

## 6. W8A8 验证层级

1. ModelSlim 配置解析单测；
2. 权重加载完整性；
3. 单个 global/sliding layer；
4. Dense/MoE 服务拉起；
5. 文本和图片 smoke；
6. eager/graph；
7. 小规模精度；
8. 全量精度；
9. 固定 workload 性能；
10. TP/EP 组合。

10 题 90% 只能作为 smoke，不应成为正式 baseline。

这个顺序的价值在于定位成本。完整 GPQA-D 很贵，如果权重 mapping 在第 2 步就错了，没有必要先跑数小时精度；反过来，服务成功生成一句话后也不能跳过第 7–9 步。量化误差是否可接受，最终必须由代表性精度和固定 workload 性能共同回答。

## 7. 已有 W8A8 性能证据

性能分支中验证了：

- 31B Dense W8A8；
- 26B MoE only-experts W8A8_DYNAMIC；
- v1 engine；
- TP1；
- 显式 PIECEWISE；
- 文本和图片 workload；
- 100% 请求成功。

详细数据见 [05 精度、性能基线与调优](05_精度性能基线与调优.md)。

为什么还要分别测文本和图片？因为多模态请求的 prefill 更长，encoder/projector 与语言模型的耗时占比也不同。W8A8 对 decode MLP 的收益可能很明显，却被视觉 encoder 或长 prefill 稀释。只有拆开 workload，才能知道优化到底加速了哪一段。

## 8. 量化适配边界

当前基线已覆盖 31B Dense W8A8 和 26B MoE only-experts W8A8，但不能自动外推到：

- E2B/E4B；
- 所有 ModelSlim checkpoint 版本；
- A2/A5；
- TP2/TP4；
- 量化 MTP；
- 超长上下文；
- FULL_DECODE_ONLY。

新增量化 checkpoint 时必须重新核对 quant description、实际 tensor 列表和模型 revision。
